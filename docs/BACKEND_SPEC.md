# ТЗ бэкенда прототипа ассистента ekt.kz

Версия контракта: 2, 2026-09-23. Общий контракт бэкенда, ассистента и фронтенда; синхронизирован с [AI_ARCHITECTURE_PLAN.md](AI_ARCHITECTURE_PLAN.md). Документ описывает целевую реализацию, а не уже работающие функции.

## 1. Результат и границы

Сделать бэкенд на существующем FastAPI: каталог ekt.kz → диалог → предложение конкретных товаров и количества → явное подтверждение → сохранённая корзина → ссылка на её страницу.

Корзина принадлежит нашему прототипу. Она не изменяет корзину ekt.kz, не резервирует складские остатки, не создаёт заказ и не принимает оплату. Страница `/cart` на нашем фронтенде должна показывать реальное серверное состояние. Одна API без этой страницы не закрывает демонстрацию ссылки на корзину. Соответствие собственной корзины требованию интеграции с ekt.kz остаётся ограничением прототипа, которое нужно указать в README и на защите.

Текущее состояние репозитория: `backend/main.py` — FastAPI с `/health/`; фронтенд — React/Vite. Django не добавлять. Основное хранилище по решению владельца — PostgreSQL: каталог, сессии, сообщения, корзины, предложения и метаданные вложений. Подключение через `DATABASE_URL`, работа через SQLAlchemy и PostgreSQL-драйвер. Redis, очередь задач и отдельная векторная БД в первой версии не требуются. PostgreSQL выбран для конкурентных транзакций и развития поиска; ускорение внешних API или всего ответа этим выбором не гарантируется. Подключение БД ещё предстоит реализовать.

## 2. Владельцы и стык команды

| Участник | Его работа |
|---|---|
| Данияр, бэкенд | API, интеграция каталога, нормализация данных, поиск, сессии, хранение сообщений и вложений, предложения корзины, подтверждение, проверки остатков, ошибки |
| Разработчик ассистента | OpenAI, инструкция модели, вызовы разрешённых инструментов, понимание запроса, извлечение данных из вложений, ранжирование кандидатов и объяснение аналогов |
| Разработчик фронтенда | Чат, загрузка вложений, карточки, экран предложения, кнопки подтверждения/отмены, страница корзины, мобильная версия |

Предлагаемые границы файлов: Данияр — `backend/` кроме `backend/assistant/`; разработчик ассистента — `backend/assistant/`; фронтендер — `frontend/`. Этот контракт и границы нужно передать обоим до начала параллельных правок. Изменения `requirements.txt` согласовывать, поскольку файл общий.

Ассистент подключается как Python-модуль внутри бэкенда. Он не получает произвольный доступ к БД корзины и не выполняет её подтверждение. Конкретный интерфейс модуля описан в разделе 8.

## 3. Общие правила API

- Базовый путь: `/api`. Существующий `/health/` сохранить.
- JSON в UTF-8. Даты — ISO 8601 UTC. ID товара ekt.kz — целое число, остальные ID — непрозрачные UUID.
- Деньги и количества в публичном API — десятичные строки: `"64920.00"`, `"2"`, `"1.5"`. В расчётах использовать Decimal, не float. Валюта прототипа — KZT из конфигурации.
- В PostgreSQL деньги хранить как NUMERIC(18,2), количества как NUMERIC(18,3); исходные карточки и структурированное состояние — JSONB. Индексировать артикулы, product_id, session_id; уникальность товара в корзине и сессионного токена обеспечить ограничениями БД. Миграции схемы хранить в репозитории.
- Гостевой пользователь определяется случайным непрогнозируемым токеном в HttpOnly-cookie. Сессия, сообщения, корзина, предложения и вложения связаны на сервере. ID из запроса не заменяет проверку владельца.
- Cookie: SameSite=Lax, Secure при HTTPS. Фронтенд и API работают через один origin; в разработке фронтендер настраивает Vite proxy для `/api`.
- При создании сессии выдавать CSRF-токен. Изменяющие запросы требуют `X-CSRF-Token`; проверять допустимый Origin. Создание новой пустой сессии освобождено от CSRF, но не от проверки Origin.
- Ответ об ошибке: `{"error":{"code":"INSUFFICIENT_STOCK","message":"Доступно 3, в корзине уже 1","details":{}}}`. Не отдавать клиенту traceback, заголовки авторизации или ключи.

## 4. Данные и каталог

### Источник

- `GET https://ekt.kz/api/products?page=N&per_page=100` — список, проверено получение увеличенной страницы.
- `GET https://ekt.kz/api/products/detail?id=ID` — карточка, цена, общий остаток, склады, описание и свойства.
- Basic Auth использовать только на сервере. Переменные: `EKT_API_BASE_URL`, `EKT_API_USERNAME`, `EKT_API_PASSWORD`.
- `url` — публичная страница товара; `url_api_detail` — адрес JSON для серверной интеграции. Не путать их и не отправлять клиенту учётные данные.

Не требуется импортировать все 15 тысяч подробных карточек. Сделать команду загрузки ограниченной выборки с параметром лимита; взять минимум две категории, позиции с нулевым и положительным остатком, проверяемую пару аналогов и товар с документом. Сохранить выборку локально, чтобы поиск не перелистывал API при каждом сообщении. Для неизвестного ID разрешён прямой запрос карточки. В README честно указать охват поиска.

Уточнение проверки 2026-09-23: список содержал 15 035 уникальных ID; при `per_page=100` страница 151 вернула 35 позиций. Проверены 11 258 подробных карточек, затем обход остановлен владельцем. Дальняя страница может повторять первую: наличие 20 элементов на странице 1600 не доказывает наличие 32 000 товаров. Импорт должен останавливаться также при повторе страницы/отсутствии новых ID. Это результат конкретной выгрузки, а не постоянный размер каталога.

### Нормализованная карточка

```json
{
  "id": 515291,
  "article": "200300285_",
  "supplier_article": "027228",
  "name": "027228 АВ DRX250 MT 3ф 160А 18ka Legrand (1)",
  "category": "Автоматические выключатели",
  "price": "64920.00",
  "currency": "KZT",
  "available_quantity": "23",
  "stock_scope": "all_warehouses",
  "unit": "piece",
  "quantity_step": "1",
  "stores": [{"id": 13, "name": "Алматы", "quantity": "5"}],
  "description": "Описание из API",
  "characteristics": [{"code": "NOMINALNYY_TOK", "name": "Номинальный ток", "value": "250 А"}],
  "documents": [],
  "product_url": "https://ekt.kz/catalog/.../",
  "image_url": "https://ekt.kz/upload/...jpg",
  "data_warnings": ["В названии 160 А, в NOMINALNYY_TOK 250 А; значение требует уточнения"],
  "checked_at": "2026-09-23T09:00:00Z"
}
```

Это пример структуры: список складов в нём сокращён, ссылки с многоточием не являются рабочими. Категорию нормализовать из проверенных свойств/пути каталога; технический код свойства не всегда достоверно описывает его смысл. Для выбранных категорий сделать явное сопоставление полей. Сохранить исходный JSON для проверки источника, но не передавать весь его объём модели.

Правила:

1. Поиск: точный внутренний или поставщицкий артикул выше совпадения по словам названия; максимум 20 результатов на страницу.
2. `quantity` — общий остаток, `stores` — остатки по складам. Общий остаток не означает наличие в городе клиента. Для первой версии корзина проверяется по общему `quantity`; выбор и резервирование склада не реализуются.
3. У некоторых товаров `quantity` не содержит дробную часть суммы складов. Не заменять его суммой молча; использовать общий остаток как консервативный предел и сохранять предупреждение о расхождении.
4. Для выборки явно задать единицы и шаг продажи по проверенным данным. `KRATNOST_MIN` — кандидат для шага, но не автоматически доказанный минимум заказа. Если единица/шаг неоднозначны, `unit`/`quantity_step` возвращаются null и покупка этой позиции блокируется до настройки. Сложные единицы не угадывать по названию.
5. Нулевая/отрицательная или неизвестная цена означает, что подтверждение покупки недоступно. Не считать товар бесплатным.
6. Известные противоречия характеристик хранить в `data_warnings`. Для демовыборки достаточно проверенной разметки; не строить универсальный аудит каталога. Товары с противоречивыми критичными параметрами исключать из автоматического подбора аналогов.
7. Для кандидатов в аналоги сервер возвращает реальные карточки и сопоставимые свойства. Ассистент выбирает и объясняет. Бэкенд отбрасывает несуществующие/недоступные позиции; для выбранных категорий фильтрует по согласованным критичным параметрам. Одинаковый бренд или похожее название сами по себе не доказывают совместимость. При недостатке сведений не обещать заменяемость.

### Документы и условия покупки

- У товара 21449 (артикул `010500006_`) найдены `FILES_CERTIFICATES`, `FILES_PASSPORTS` и другие поля. Они содержат ID файлов; прямые ссылки есть на публичной странице товара.
- Для демовыборки извлечь ссылки на документы из страниц товаров и сохранить: `type`, `title`, `url`, `source_url`. Разрешены только проверенные адреса источника, а не произвольные URL от модели. Не называть отказное письмо сертификатом. Наличие файла не доказывает актуальность или применимость его содержания.
- Если ссылки нет, вернуть пустой список документов, а не придумывать адрес по ID.
- Условия покупки хранить отдельной небольшой базой фактов из `https://ekt.kz/checkout-delivery/`: способ оплаты, доставка, самовывоз, ссылка и время проверки.
- На странице есть разные пороги бесплатной доставки: 30 000 ₸ в основном тексте и 15 000 ₸ в повторяющемся блоке. Сохранить это как конфликт источника; ассистент не должен безоговорочно обещать бесплатную доставку на спорных условиях. Оплату и бесспорные условия можно сообщать со ссылкой.

## 5. Минимальное хранение

| Сущность | Поля/назначение |
|---|---|
| Session | ID, хеш случайного cookie-токена, CSRF, preferred_language (ru/kk/en), состояние, время создания/истечения |
| ProductSnapshot | ID ekt, артикулы, нормализованные данные, исходный JSON, время обновления |
| Message | ID, session_id, роль user/assistant, текст, attachment_ids, время |
| Attachment | ID, session_id, безопасный путь, оригинальное имя, определённый тип, размер, время удаления |
| Cart | ID, session_id, revision |
| CartItem | cart_id, product_id, количество, подтверждённая цена, название, единица, время проверки |
| CartProposal | ID, session_id, базовая revision корзины, позиции/цены, expires_at, статус, сохранённый результат подтверждения |

Одна корзина на сессию, одна строка на товар, одно действующее предложение на сессию. Новое предложение отменяет предыдущее. Корзина и подтверждение сохраняются в PostgreSQL, а не в глобальном словаре процесса. При перезапуске сервера корзина сохраняется.

## 6. HTTP-контракт для фронтенда

| Метод и путь | Вход | Результат |
|---|---|---|
| `POST /api/session` | `{}` | cookie, `csrf_token`, `expires_at`; для действующей cookie возвращает текущую сессию |
| `GET /api/products` | `q`, `limit` ≤ 20, `offset` | `{items, total, catalog_scope}`; `catalog_scope: "demo_subset"` при ограниченной выборке |
| `GET /api/products/{id}` | — | нормализованная карточка; 404, если товара нет |
| `GET /api/products/{id}/analogs` | `limit` ≤ 5 | кандидаты с карточками, совпадениями/различиями; допускается пустой список |
| `GET /api/purchase-conditions` | — | факты, источники, предупреждения о противоречиях |
| `POST /api/attachments` | multipart `file` | `{attachment_id, filename, media_type, size}` |
| `GET /api/attachments/{attachment_id}` | — | файл только владельцу сессии; 404 для чужого/истёкшего ID |
| `GET /api/chat/messages` | `limit` ≤ 50, необязательный `before_id` | `{items, next_before_id}`; только текущая сессия, сообщения в хронологическом порядке |
| `POST /api/chat/messages` | `{text, attachment_ids: [], language: null}` | ответ ассистента, карточки, предложение или результат подтверждения |
| `GET /api/cart` | — | текущее состояние корзины |
| `POST /api/cart/proposals` | `{items: [{product_id, quantity}]}` | проверенное предложение на добавление; корзина ещё не меняется |
| `POST /api/cart/proposals/{id}/confirm` | `{confirmed: true}` | обновлённая корзина и `cart_url` |
| `POST /api/cart/proposals/{id}/cancel` | `{}` | `{status: "cancelled"}`; корзина не меняется |
| `GET /health/` | — | liveness приложения, существующий маршрут |
| `GET /ready` | — | readiness приложения и PostgreSQL; 503 при неготовности, без вызова ekt.kz/OpenAI |

`GET /cart` обслуживает фронтенд. Поле `language` принимает `ru`, `kk`, `en` или null; явный выбор сохраняется в сессии, иначе ассистент определяет язык по сообщению. Количества в запросах — строки. Единственные имена общего контракта: `text`, `proposal`, `proposal.id`; варианты `/api/chat`, `/api/cart/prepare`, `/api/cart/confirm`, `message`, `pending_action` и `action_id` в публичном HTTP-контракте не используются.

Первая версия поддерживает добавление. Изменение количества, удаление и очистку корзины не выставлять отдельными обходными маршрутами: если добавлять эти функции позже, им тоже требуется явное подтверждение.

### Ответ чата

```json
{
  "message_id": "uuid",
  "language": "ru",
  "text": "Нашёл товар. Добавить 2 штуки?",
  "products": [],
  "proposal": {
    "id": "uuid",
    "status": "pending",
    "expires_at": "2026-09-23T09:10:00Z",
    "items": [{"product_id": 123, "name": "Товар", "quantity": "2", "unit_price": "100.00", "line_total": "200.00"}],
    "total": "200.00",
    "currency": "KZT"
  },
  "cart": null,
  "cart_url": null,
  "warnings": []
}
```

`products` — нормализованные карточки из раздела 4, выбранные по проверенным ID. `proposal` — null, если предложения нет. После успешного подтверждения `proposal` можно вернуть со статусом confirmed, а `cart` и `cart_url` заполнить. Фронтенд не извлекает команды и цены из текста ответа — использует структурированные поля.

### Корзина

```json
{
  "id": "uuid",
  "revision": 1,
  "items": [{"product_id": 123, "name": "Товар", "quantity": "2", "unit": "piece", "unit_price": "100.00", "line_total": "200.00", "price_checked_at": "2026-09-23T09:01:00Z"}],
  "line_count": 1,
  "total": "200.00",
  "currency": "KZT",
  "cart_url": "/cart"
}
```

`cart_url` формирует сервер из конфигурации приложения; модель не придумывает ссылки. На нашем origin достаточно `/cart`: состояние определяется cookie, секретные токены в URL не помещать. `GET /api/cart` не меняет состав и подтверждённые цены автоматически. Время проверки цены видно в ответе; итог — сумма подтверждённых позиций, а не обещание будущей цены на сайте партнёра.

## 7. Подтверждение и остатки — обязательная бизнес-логика

1. Предложение содержит определённые товары, количество и цены. Перед его выдачей проверить существование товаров, шаг количества, положительную цену и достаточный остаток с учётом уже имеющейся корзины. Предложение живёт 10 минут и связано с текущей revision корзины.
2. Ни поиск, ни запрос «сколько стоит», ни предложение ассистента не меняют корзину.
3. Основной способ подтверждения — кнопка фронтенда с вызовом `/confirm`. Для текстового сценария сервер распознаёт только полные фразы после нормализации регистра/пробелов: `да, добавь`, `да добавь`, `подтверждаю добавление`. Они работают только при одном действующем предложении, уже выданном в этой сессии. Простое «да», цитата, вложение и текст ответа модели подтверждением не являются.
4. Текстовое подтверждение обрабатывается до вызова модели и вызывает ту же серверную функцию, что `/confirm`. Если предложения нет/оно устарело, вернуть объяснение без изменения корзины.
5. При подтверждении повторно запросить свежие цену и общий остаток из ekt.kz. Кэш для этой проверки не использовать. Если API недоступен, корзина остаётся прежней; нельзя подтверждать по старому остатку.
6. Для каждого товара должно выполняться: `уже_в_корзине + добавляемое_количество <= свежий_остаток`. Числа конечные, больше нуля, соответствуют шагу. Отрицательные значения, ноль, NaN/Infinity и избыточная точность отклоняются. Повторяющиеся ID в предложении предварительно объединяются и проверяются как одна позиция.
7. Если остатка не хватает — 409 `INSUFFICIENT_STOCK`, показать доступное количество. Не уменьшать запрошенное количество автоматически. Если цена изменилась — 409 `PRICE_CHANGED`, старое предложение не подтверждать; новое предложение с новой ценой требует нового согласия.
8. Проверить владельца предложения, срок, статус и revision. Подтверждение чужого ID — 404. Истёкшее/заменённое предложение или изменившаяся корзина — 409. Нужен новый просмотр и подтверждение.
9. Применять предложение целиком в транзакции PostgreSQL. Если хотя бы одна позиция не прошла, не добавлять ничего. Блокировать строку корзины и предложения в едином порядке через `SELECT FOR UPDATE`, внутри транзакции повторно проверить revision и статус. Сетевые запросы выполнять до взятия блокировок; изменившаяся за это время revision приводит к 409. Переход pending → confirmed, запись позиций и результата подтверждения коммитятся вместе.
10. ID предложения — ключ идемпотентности. Повторное или одновременно пришедшее подтверждение того же предложения не добавляет товар второй раз, возвращает сохранённый результат. Проверка принадлежности сессии обязательна и при повторе.
11. После успеха увеличить revision и вернуть корзину с `/cart`. Проверка внешнего остатка отражает момент запроса и не является резервированием на складе ekt.kz.

## 8. Контракт с разработчиком ассистента

Согласовать функцию `async reply(context, tools) -> AssistantResult` в `backend/assistant/service.py`. Её реализует разработчик ассистента, бэкенд вызывает её из обработчика чата.

`context`:

```json
{
  "text": "Нужен аналог этого автомата, 2 штуки",
  "language": "ru",
  "history": [{"role": "user", "text": "..."}, {"role": "assistant", "text": "..."}],
  "attachments": [{"id": "uuid", "filename": "spec.xlsx", "media_type": "...", "storage_path": "server-only-path"}],
  "cart": {"items": []},
  "pending_proposal": null
}
```

`storage_path` доступен только внутреннему модулю, не отправляется браузеру и не включается в текст для модели. Бэкенд передаёт только принадлежащие сессии вложения. История для модели ограничена последними 8–12 сообщениями; полная история остаётся в хранилище сессии.

Бэкенд предоставляет модулю только инструменты чтения:

- `search_catalog(query, article, filters, limit)`;
- `get_product(product_id)`;
- `find_analogs(product_id, required_quantity)`;
- `get_purchase_terms(topic)`;
- `get_cart()`.

Результат модуля:

```json
{
  "language": "ru",
  "text": "Нашёл подходящие варианты…",
  "product_ids": [123],
  "proposed_items": [{"product_id": 123, "quantity": "2"}],
  "warnings": []
}
```

Бэкенд проверяет схему, ID и количество, сам наполняет карточки, сам создаёт pending-предложение из `proposed_items`. Цены, остатки, totals, подтверждение и URL корзины от модели не принимаются. `proposed_items: []` означает отсутствие предложения. У модели нет инструмента подтверждения корзины или отдельного `prepare_cart_add`: создание предложения происходит один раз после валидации результата модуля. Подписи инструментов и ответ модуля совпадают с разделом «Граница ответственности ИИ» AI-плана. Внутренние данные могут содержать подробные доказательства конфликтов; наружу бэкенд преобразует их в карточку из раздела 4.

Зона ассистента: сведения о товарах и вложения считаются недоверенными данными, а не инструкциями; ответ опирается на результаты инструментов; аналог объясняется конкретными свойствами и оговорками. Ошибка OpenAI возвращается как понятная ошибка сервиса, без выдуманного успешного ответа. До готовности модуля можно проверять API и корзину напрямую; отключённый AI возвращает `ASSISTANT_UNAVAILABLE`, не имитацию работающей модели.

## 9. Вложения, ошибки и приватность

- В ТЗ указаны Excel, Word, PDF и JPEG. Бэкенд принимает и хранит файлы; извлечение текста/таблиц/изображений делает участник ассистента. До реализации согласовать конкретные расширения: `.xlsx`, `.xls`, `.docx`, `.doc`, `.pdf`, `.jpg`, `.jpeg`. Если обработчик не поддерживает формат, вернуть явный отказ, а не сообщать, что файл прочитан.
- Лимиты прототипа: до 10 МБ на файл, до 3 вложений на сообщение, текст до 8 000 символов. Проверять фактический тип файла, размер и принадлежность сессии. Не исполнять макросы; не использовать пользовательское имя как путь.
- Хранить загрузки вне публичной статики под случайными именами. Не открывать произвольные URL из сообщений как вложения. Вложения удалять через 1 час; срок гостевой сессии/истории/корзины — 24 часа. Нужна простая команда очистки, без отдельного сервиса.
- Не запрашивать платёжные реквизиты; не записывать содержимое вложений, переписку и секреты в технические логи. Логировать ID запроса, длительность, код ответа внешнего API и категорию ошибки.
- Ограничить число одновременных AI-запросов и частоту запросов на сессию. Для прототипа достаточно одного процесса и локального ограничения, например 10 сообщений в минуту на сессию. Это ограничение не является защитой от распределённого злоупотребления.
- Для каталога установить сетевой timeout 5 секунд и не более одного повторения безопасного GET при временной сетевой ошибке/5xx. При 401/403 не повторять. Для AI ограничить время ожидания, например 20 сек.; целевой ответ в единицы секунд проверяется замером основного сценария, а не обещается заранее.
- Основные ошибки: 404 `PRODUCT_NOT_FOUND`; 422 `INVALID_QUANTITY`; 413 `FILE_TOO_LARGE`; 415 `UNSUPPORTED_FILE_TYPE`; 409 `INSUFFICIENT_STOCK`, `PRICE_CHANGED`, `PROPOSAL_EXPIRED`, `PROPOSAL_REPLACED`, `CART_CHANGED`; 422 `PRODUCT_NOT_PURCHASABLE`; 502 `CATALOG_UNAVAILABLE`; 503 `ASSISTANT_UNAVAILABLE`; 429 `RATE_LIMITED`.

## 10. Порядок реализации и приёмка

### Порядок

1. Передать участникам разделы 2, 3, 6 и 8, закрепить формат ответа и владение файлами.
2. Настроить конфигурацию, PostgreSQL и миграции, сессию, клиент ekt.kz и небольшую проверенную выборку. Реализовать поиск и карточку.
3. Сделать корзину, предложения и единый механизм подтверждения. Проверить их напрямую через API, не ожидая AI.
4. Добавить условия покупки, ссылки на документы и кандидатов аналогов. Подключить готовый модуль ассистента и историю.
5. Соединить чат с фронтендом, затем загрузку файлов с обработчиком ассистента. Сделать один сквозной показ.

### Достаточные проверки

| Сценарий | Ожидаемый результат |
|---|---|
| Существующий артикул | Карточка соответствует данным источника, есть склады и доступный документ, если найден |
| Отсутствующий товар из подготовленной пары | Возвращается минимум один доступный кандидат, ассистент объясняет различия |
| Вопрос об оплате/доставке | Содержательный ответ по источнику; конфликт порогов не скрывается |
| Создание предложения без согласия | Корзина остаётся пустой |
| Кнопка подтверждения и отдельный сценарий «да, добавь» | Товары добавлены, ответ содержит рабочий `/cart` |
| Тот же товар уже есть в корзине | Проверяется итоговое количество, а не только добавляемое |
| Двойное/одновременное подтверждение | Одна операция добавления |
| Недостаток остатка в одной строке многострочного предложения | 409, ни одна строка не добавлена |
| Цена/остаток изменились либо ekt.kz недоступен | Нет молчаливой замены цены, количества или подтверждения по кэшу |
| Чужая сессия / нет CSRF / истёкшее предложение | Нет доступа и изменения корзины |
| Перезагрузка страницы и перезапуск бэкенда | Та же сессия видит сохранённую корзину |
| Файл поддерживаемого типа / неподдерживаемый файл | Ассистент использует реально извлечённые данные / явная ошибка формата |

Для проверок изменения остатков/цены допустим управляемый тестовый клиент каталога; отдельно выполнить один реальный read-only запрос к ekt.kz. Нужны точечные проверки бизнес-логики и один сквозной сценарий, не полный аудит проекта.

### Что сдаёт бэкенд

- Работающие маршруты и схема API, доступная фронтендеру и автору ассистента.
- `.env.example` без значений секретов: настройки EKT, `DATABASE_URL`, origin приложения, режим Secure-cookie, лимиты; `OPENAI_API_KEY` использует серверный модуль ассистента.
- Проверенная демонстрационная выборка и способ её загрузки; загруженные файлы клиентов и секреты в git не попадают.
- README с запуском, проверками, источниками, границами выборки и явными ограничениями собственной корзины, отсутствия резерва и конфликтующих данных.

Создание коммита или push этим ТЗ не разрешается: для каждого требуется отдельное указание владельца.
