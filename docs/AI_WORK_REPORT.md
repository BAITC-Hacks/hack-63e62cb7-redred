# Отчёт по AI-направлению RedRed

Дата: 2026-09-23
Статус: AI-модуль подключён к HTTP- и WebSocket-маршрутам backend; реальные HTTP-сценарии с OpenAI и ЕКТ проверены. Пользовательский frontend и сквозной браузерный сценарий ещё не готовы.

## 1. Цель работы

Подготовить минимальную проверяемую логику AI-ассистента для ekt.kz, который:

- отвечает по характеристикам, наличию, сертификатам и условиям покупки;
- показывает противоречия в исходных данных, а не выбирает значение наугад;
- предлагает объяснимые аналоги при отсутствии товара;
- работает на русском, казахском и английском;
- не изменяет корзину без явного подтверждения пользователя;
- использует API-каталог и инструменты, а не знания модели, для фактов о товарах;
- передаёт текст ответа после проверки инструментов частями через событие чата; итоговый структурированный результат проверяется отдельно.

## 2. Итоговое архитектурное решение

Основная модель прототипа — `gpt-6-sol` через OpenAI Responses API. NVIDIA API остаётся резервным провайдером для отдельного сравнительного теста. Одновременно вызывать двух провайдеров для каждого сообщения не требуется.

vLLM в текущей конфигурации не нужен: OpenAI и NVIDIA предоставляют управляемые API. vLLM имеет смысл только при дальнейшем самостоятельном размещении open-source модели на своей GPU-инфраструктуре.

Пайплайн:

```text
Пользователь
  → HTTP/WebSocket backend (frontend пока заглушка)
  → загрузка сессии, истории, корзины и вложений
  → LLM определяет намерение и вызывает read-only tools
  → backend получает и нормализует данные каталога
  → backend отмечает конфликты и проверяет факты
  → LLM формирует структурированный AssistantResult
  → backend валидирует результат
  → backend отдаёт проверенный текст одной дельтой и итоговый result
```

Read-only инструменты AI-модуля:

```text
search_catalog(query, article, limit)
get_product(product_id)
find_analogs(product_id, required_quantity)
get_purchase_terms()
get_cart()
```

LLM не получает инструмент непосредственного изменения корзины. Его структурированный результат содержит только предложение:

```json
{
  "language": "ru",
  "text": "Нашёл товар. Добавить 2 штуки?",
  "product_ids": [515291],
  "proposed_items": [
    {"product_id": 515291, "quantity": "2"}
  ],
  "warnings": []
}
```

Backend самостоятельно валидирует `product_ids` и `proposed_items`, перечитывает цену и остаток и создаёт pending proposal. Корзина изменяется отдельной серверной операцией только после явного подтверждения.

## 3. Логика корзины

1. Запрос пользователя «добавь 2 штуки» создаёт только предложение.
2. Будущий frontend должен показать состав предложения и кнопку «Да, добавить»; сейчас это можно проверить через HTTP API.
3. Простое «да» без действующего предложения ничего не меняет.
4. После подтверждения backend повторно проверяет цену и остаток в EKT.
5. Если EKT недоступен, остаток изменился или товара недостаточно, операция блокируется.
6. Backend проверяет сессию, срок действия, revision и идемпотентность proposal.
7. Все позиции добавляются транзакционно либо не добавляется ни одна.
8. После успеха возвращается актуальная корзина и ссылка `/cart`.

У модели нет права подтверждать операцию, вычислять итоговую цену или придумывать URL корзины.

## 4. RAG и защита от ошибок каталога

Для MVP выбран простой retrieval без обязательной vector database:

1. точное совпадение артикула;
2. полнотекстовый или нечёткий поиск по локальному индексу;
3. фильтрация по категории и проверенным характеристикам;
4. получение detail-карточки для актуальной цены и остатка;
5. формирование ответа моделью только по результатам tools.

Название, описание, свойства карточки и пользовательские файлы считаются недоверенными данными. Они не могут менять system prompt или инициировать изменение корзины.

В реальной карточке `id=515291` подтверждён конфликт:

- название и описание: 160 А;
- `properties.NOMINALNYY_TOK`: 250 А.

Ассистент должен показать оба значения, добавить предупреждение и не использовать спорный параметр как доказательство совместимости аналога.

Аналог считается кандидатом только при совпадении важных проверенных параметров и положительном остатке. Если полная совместимость не доказана, ответ должен говорить «похожий товар, проверьте совместимость», а не «полный аналог».

## 5. WebSocket и метрики задержки

Типы событий согласованного backend-контракта:

```text
message.accepted    сообщение принято
processing.status   безопасный статус, например «Проверяю каталог»
products.ready      проверенные карточки
assistant.delta     поток текста после получения нужных фактов
assistant.completed итоговый структурированный ответ
error               понятная ошибка
```

Факты о цене, остатке и характеристиках нельзя отправлять до завершения соответствующего tool call.

Измеряемые значения:

- `ttft_ms` — время до первого текстового токена;
- `tool_duration_ms` — время внешнего инструмента;
- `completion_ms` — время генерации модели;
- `duration_ms` — полная задержка сообщения.

Отдельный реальный streaming-прогон OpenAI показал:

- первое SSE-событие: 1 098 мс;
- первый текстовый delta: 2 170 мс;
- завершение ответа: 2 402 мс;
- 29 входных и 52 выходных токена.

Это единичное измерение и ориентир, а не SLA.

## 6. История и языки

В модель передаются:

- инструкции AI-сервиса;
- выбранный или определённый язык;
- до 12 последних завершённых сообщений с ограничением объёма;
- структурированное состояние корзины и pending proposal;
- результаты tools.

Отдельный summary старой части диалога сейчас не создаётся. Вызовы провайдера выполняются с `store=false`. Цена, остаток и подтверждение берутся из backend/каталога, а не из текста истории.

Ассистент отвечает на языке текущего сообщения либо на явно выбранном языке сессии: `ru`, `kk` или `en`. Артикулы, числа, единицы измерения и названия брендов не переводятся.

Текущий контракт команды в `origin/main` выбирает PostgreSQL основным источником истории, сессий и корзины. Первоначальная идея Redis расходится с этим решением. Если Redis останется в Docker, его рекомендуется использовать только для короткого кэша, rate limiting и состояния WebSocket, не создавая второй источник истины.

## 7. Вложения

Целевой сценарий обработки вложений (загрузка, ограниченный разбор и передача в модель реализованы; сквозные запросы JPEG и PDF проверены на двух образцах):

```text
проверка размера и реального MIME
  → безопасное временное хранение
  → извлечение содержимого
  → сопоставление позиций с каталогом
  → уточнение неоднозначных совпадений
  → предложение товаров
  → отдельное подтверждение корзины
```

Текущая поддержка форматов:

1. DOCX и XLSX: ограниченное локальное извлечение текста; формулы XLSX не исполняются.
2. JPEG: передача изображения модели.
3. PDF: передача файла модели, без локального OCR и без гарантии распознавания скана.
4. Старые DOC/XLS не поддерживаются.

Неподдерживаемый файл должен давать явную ошибку. Нельзя сообщать, что документ прочитан, если извлечение не выполнено.

## 9. Результаты проверок

### OpenAI

- API-доступ к `gpt-6-sol` подтверждён.
- Базовый набор: 9/9 пройдено.
- Проверены structured intent на русском, казахском и английском.
- Проверены выбор tools, отсутствие записи в корзину и prompt injection из карточки.
- Предыдущая версия диалогового tool loop прошла 5/5 сценариев.
- После получения общего backend-контракта eval изменён с `prepare_cart_add` на `proposed_items`; эту обновлённую версию необходимо повторно прогнать после объединения ветки.
- Streaming probe прошёл успешно, TTFT составил 2 170 мс.
- Текущий `backend/assistant/service.py` возвращает `AssistantResult` по контракту backend: максимум два вызова модели, до трёх свежих карточек и только инструменты чтения. Он не даёт модели инструмента подтверждения корзины.
- Сохранённый `ai/reports/backend-ai-live.json` содержит четыре успешных HTTP-сценария с реальными OpenAI и EKT: условия покупки (5,5 с), карточка и предложение (6,593 с), подтверждение (0,235 с), аналог (7,266 с). Это отдельные запросы, не браузерный сценарий и не p95.

### EKT

Первый ограниченный запуск получил:

- 3 страницы, 60 элементов списка;
- 10 успешных detail-карточек из 12;
- 2 товара с нулевым остатком;
- 2 карточки с `RECOMMEND`;
- конфликт 160 А/250 А;
- совпадение общего остатка с суммой складов в проверенных карточках;
- среднюю задержку detail около 6,25 секунды;
- 2 таймаута.

Следующий короткий прогон не получил список и detail-карточку после двух попыток. Последний сохранённый EKT-отчёт поэтому имеет статус `partial`. Это подтверждает необходимость локального индекса, timeout и понятного fallback.

### Локальные проверки

1. Собрать frontend-чат и страницу `/cart`, подключить сессию/CSRF, WebSocket `/api/chat/ws` и HTTP-подтверждение proposal по `BACKEND_SPEC.md`.
2. Проверить в браузере весь путь: сообщение → проверенная карточка → предложение → явное подтверждение → свежая проверка остатка → обновлённая корзина `/cart`.
3. Проверить WebSocket именно в браузере и хотя бы один полный сценарий на каждом заявленном языке. Backend WebSocket, JPEG/PDF проверены ограниченными реальными запросами; другие файлы требуют отдельных сквозных проверок.

5. Получить от партнёра разрешённый write API/SDK, если требуется именно корзина ekt.kz. Пока доступен только read API и корзина прототипа.

## 11. Текущий Git-статус и риски

На момент этой ревизии локальная ветка соответствует `origin/main` на коммите `9b12a5a`, но AI-модуль, тесты, отчёты и изменения документации находятся в рабочем дереве: они ещё не закоммичены и недоступны другим участникам через Git. Перед объединением проверить актуальный `git status`, так как команда работает параллельно.

Основные риски:

- отсутствует способ записи в настоящую корзину ekt.kz;
- EKT API нестабилен и не укладывается в желаемую задержку без локального индекса;
- WebSocket-маршрут проверен через тестовый клиент с реальными OpenAI/EKT, но браузерная проверка с frontend не выполнена;
- единая схема сертификатов не подтверждена;
- опубликованные пороги бесплатной доставки противоречат друг другу;
- локальная обработка DOCX/XLSX проверена unit-тестом; JPEG/PDF прошли ограниченную сквозную проверку, но распознавание произвольных документов не гарантировано.

## 12. Точка продолжения

Следующий шаг — не новое проектирование, а браузерная проверка уже реализованных backend/AI-частей:

```text
сообщение в WebSocket
  → search/get_product tool
  → проверенная карточка
  → части текста после проверки инструментов
  → proposed_items
  → backend proposal
  → явное подтверждение
  → свежая проверка остатка
  → транзакционное обновление корзины
  → /cart
```

Аналоги, условия покупки, JPEG и PDF прошли ограниченные реальные HTTP-прогоны. После стабильной работы основного браузерного сценария проверить DOCX/XLSX и языки; не выдавать отдельные проверки за завершённый пользовательский продукт.
