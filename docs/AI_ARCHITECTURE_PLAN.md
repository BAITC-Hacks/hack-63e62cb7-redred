# RedRed — проверенный курс для кейса ekt.kz

Дата ревизии: 2026-09-23. Это план прототипа, а не описание уже реализованных функций. В репозитории пока есть только каркас FastAPI и React; README не содержит инструкции запуска решения.

## Решение по гипотезе

Направление верное: ассистент должен понимать свободный запрос, а факты о товарах получать из каталога; подтверждение и изменение корзины должны контролироваться сервером. Прежний план пытался реализовать полный обход каталога, vector RAG, все форматы вложений и обширный eval-набор одновременно с обязательным сценарием. Начинаем с одного работающего пути, сохраняя согласованные Docker, Redis, Nginx и поддержку русского, казахского и английского, и расширяем retrieval и вложения только после проверки основного сценария.

Два риска для соответствия кейсу нужно решить в первый час:

1. Предоставлены только `GET /api/products` и `GET /api/products/detail?id=...`. Они не дают права или способа изменить корзину ekt.kz. Адрес существующей корзины сайта — `https://ekt.kz/personal/cart/`, но простая ссылка на него не перенесёт товары из корзины нашего прототипа. Нужны согласованный write API/SDK, тестовая среда или разрешённый способ интеграции с сессией сайта. До этого локальная корзина может демонстрировать логику подтверждения, но не закрывает интеграцию с реальной корзиной ekt.kz и переход к оформлению на сайте.
2. Условия покупки опубликованы на `https://ekt.kz/checkout-delivery/`, однако другие блоки сайта содержат иные пороги бесплатной доставки по Алматы. Для ответа можно использовать бесспорные способы оплаты и общие условия доставки со ссылкой на официальный раздел. Конкретные противоречивые суммы согласовать с партнёром. Общего правила минимальной партии пока нет; для отдельных товаров на сайте встречается поле «Кратность (мин)». Нельзя объявлять его общим правилом магазина.

## Что действительно известно о данных

- Партнёр предоставил Basic Auth и три read endpoint: `GET https://ekt.kz/api/products`, страницы списка `?page=N` и `GET https://ekt.kz/api/products/detail?id=...`. Логин и пароль не записывать в Git, frontend, документацию или логи. Хранить только в переменных окружения backend; `.env.example` должен содержать пустые `EKT_API_USERNAME` и `EKT_API_PASSWORD`.
- Read-only проверка API 2026-09-23 показала `items[]` со списком ID, артикулов и названий; карточка содержала `quantity`, `stores`, `properties`, цену и URL. Страницы вплоть до 1600 возвращали по 20 позиций, поэтому полный обход нельзя помещать в критический путь запуска. Перед реализацией повторить 2–3 безопасных GET, измерить время и сохранить обезличенную схему.
- В карточке `id=515291` ранее отмечен конфликт: название/описание указывали 160 А, поле `properties.NOMINALNYY_TOK` — 250 А. При таком конфликте показать оба значения и не использовать спорный параметр для доказательства совместимости.
- Единое поле сертификата пока не установлено. Проверить несколько реальных карточек и страницы товаров. Ссылку показывать только если она реально присутствует и открывается; иначе честно сообщать, что сертификат не найден в доступных данных.
- Репрезентативная выборка допустима по условиям кейса. Начальный локальный индекс строить из ограниченного числа страниц и заранее проверенных артикулов для демонстрации. Для товара вне индекса отвечать, что он не найден в проверенной выборке, а не что его нет во всём магазине. Полный обход каталога требует согласования лимитов API и времени.

## Минимальная архитектура

```text
Nginx: единая точка входа и проксирование /api
  -> React: чат и карточки товаров, подтверждение, просмотр корзины
  -> FastAPI: сессия, поиск, проверка фактов, AI-оркестрация, cart guard
       -> ekt.kz read API: живые детали, цена и остаток
       -> локальный индекс выборки: ID, артикул, название, несколько параметров
       -> официальный документ условий покупки
       -> OpenAI Responses API: понимание запроса и формулировка ответа
       -> Redis: история, состояние сессии, ожидающее действие и корзина прототипа
```

Использовать уже имеющиеся FastAPI и React, согласованные Redis и Nginx в Docker. Для первого рабочего сценария Redis хранит сессию и корзину; Redis Stack, embeddings и vector search не обязательны. Retrieval начинается с точного артикула, полнотекстового/нечёткого поиска по ограниченной выборке и живого detail API. Если партнёр предоставит интеграцию реальной корзины, заменить только адаптер корзины, сохранив серверную проверку подтверждения.

### Граница ответственности ИИ

- Модель извлекает намерение, артикул/описание, количество, задаёт уточнение и формулирует ответ на языке пользователя.
- Поиск точного артикула, сравнение технических параметров, источник фактов, арифметика остатков, подтверждение и запись корзины выполняются кодом backend.
- Модели доступны только read-инструменты `search_products`, `get_product`, `find_analogs`, `get_purchase_terms` и предложение подготовить добавление. Прямого `add_to_cart` у модели нет.
- Вызовы модели и её структурированный вывод валидируются. Текст карточек и вложений считается данными, а не инструкциями. При сбое модели точный поиск по артикулу и сведения из карточки продолжают работать без выдуманного AI-ответа.
- Выбор `gpt-6-sol` допустим как конфигурация: официальная OpenAI Docs подтверждает текст, изображения, function calling и structured outputs в Responses API (`https://developers.openai.com/api/docs/models/gpt-6-sol`). Фактический доступ команды, задержку и стоимость на её ключе ещё надо измерить. Если вызов не проходит, сменить конфигурируемую модель после короткого сравнительного теста.

### Сессия, история, языки и вложения

- Redis хранит `chat:{session_id}:messages`, `chat:{session_id}:state`, краткое `summary`, `cart-pending:{session_id}` и `cart:{session_id}`. Pending action живёт около 10 минут, история и корзина прототипа — до 24 часов. Критичные цена, остаток и подтверждение не восстанавливаются из LLM-summary.
- На запрос модели передаются system prompt, язык, структурированные требования, summary старой части и последние 8–12 сообщений. История управляется backend; провайдеру отправляется `store=false`, если выбранный вызов это поддерживает.
- Ассистент отвечает на русском, казахском или английском. Явный выбор языка сохраняется в сессии; иначе используется язык текущего сообщения. Артикулы, бренды, числа и единицы не переводятся. Одинаковые контрольные сценарии прогоняются на всех трёх языках.
- JPEG и сканированные страницы направляются в VLM; текстовый PDF разбирается локально, DOCX — через parser, XLSX — как таблица. Извлечённые позиции сначала сопоставляются с каталогом. Файлы и OCR-текст считаются недоверенными данными, не попадают в общий индекс и удаляются по TTL.

### Данные продукта

Backend возвращает карточку с `id`, `article`, `name`, `url`, `price`, `quantity`, `stores`, нормализованными характеристиками, ссылкой на сертификат при наличии, временем получения и предупреждениями. Цена и наличие при ответе и перед подтверждением перечитываются из детального API. Остаток по складам и город пользователя не смешивать: если доступен только общий остаток, не обещать наличие в конкретном городе.

Аналог предлагать из той же товарной категории с проверенными ключевыми параметрами и положительным актуальным остатком. Ответ должен назвать совпадения и существенные отличия. Если строгая совместимость не доказана, писать «похожий товар, проверьте совместимость», а не «полный аналог». Для теста заранее найти одну реальную отсутствующую позицию и один реальный доступный кандидат в выборке.

### Корзина

1. На просьбу купить backend создаёт ожидающее действие с конкретными `product_id`, количеством, случайным `action_id`, сроком действия и привязкой к сессии. UI показывает состав и кнопку «Да, добавить».
2. Сообщение модели и неявные фразы не меняют корзину. `POST /api/cart/confirm` принимает `action_id` из той же сессии и явное действие пользователя. Для текстового «да, добавь» нужна отдельная проверка однозначности именно текущего предложения.
3. Backend повторно получает остаток, проверяет положительное целое количество и кратность, затем одной транзакцией помечает действие использованным и обновляет корзину. Повторный запрос не добавляет товар второй раз. При изменившемся остатке выдаёт новый вариант для подтверждения.
4. Для локальной корзины ссылка ведёт на `/cart` прототипа и показывает его актуальное состояние. Ссылку `https://ekt.kz/personal/cart/` отдавать как результат добавления только после настоящей интеграции и проверки, что именно эта корзина содержит товар.

Сессия — случайный идентификатор в `HttpOnly`, `SameSite` cookie; мутацию защищать от CSRF. Цены и количество в запросе клиента не считать источником истины. Не запрашивать платёжные данные.

## Контракты первой версии

```text
POST /api/chat                   текст, язык, идентификаторы вложений при наличии
GET  /api/products/{id}          нормализованная актуальная карточка
GET  /api/cart                   корзина текущей сессии
POST /api/cart/prepare           товар и количество, без изменения корзины
POST /api/cart/confirm           подтверждение action_id
GET  /cart                       страница корзины прототипа
```

Формат ответа чата: `text`, `products[]`, `warnings[]`, `pending_action`, `cart_url`. UI берёт цену, остаток и URL из структурированного backend-ответа, не парсит их из текста модели. Контракты согласовать между тремя участниками до параллельной реализации.

Логи пишутся структурированным JSON: `request_id`, хеш сессии, событие, tool/model, статус и `duration_ms`. Не логировать Basic Auth, API-токены, cookie, полные пользовательские документы и платёжные данные.

## Порядок работ на 5 часов

| Время | Разработка и проверяемый результат |
| --- | --- |
| 00:00–00:30 | Backend проверяет 2–3 GET к API и фиксирует схему/скорость; команда запрашивает cart write интеграцию, сертификат и спорные условия доставки; вместе утверждает HTTP-контракт, тестовые товары и границы выборки. |
| 00:30–01:45 | Разработчик backend делает Basic Auth gateway, ограниченный индекс, точный поиск, свежую карточку и нормализацию. Разработчик frontend делает чат и карточку. Разработчик AI делает один рабочий Responses-вызов со структурированным намерением и fallback для точного артикула. Проверка: реальный артикул → верные факты и источник. |
| 01:45–03:00 | Backend и frontend доводят `prepare → явное confirm → повторная проверка → корзина → ссылка`. AI подключает формулировку ответа без права записи. Проверка: до подтверждения корзина пуста, после — нужное количество, повторный confirm безопасен. При наличии cart API подключить его в этот период. |
| 03:00–03:45 | Реальная отсутствующая позиция → один проверенный аналог с обоснованием. Подключить краткий источник условий оплаты/доставки; по минимальной партии отвечать только по данным товара или сообщать, что общий минимум не подтверждён. |
| 03:45–04:25 | Обработать ошибки API/модели, отсутствие сертификата, конфликт характеристики, превышение остатка; проверить мобильный экран и одинаковые базовые запросы на ru/kk/en. Затем добавить вложения, начиная с XLSX/JPEG, только если основной сценарий стабилен; PDF/DOCX заявлять лишь после фактической проверки. |
| 04:25–05:00 | Запуск с чистого окружения по README, демонстрация всех пяти must-have, проверка `.env.example`, зависимостей и отсутствия секретов. Исправлять только то, что мешает основному сценарию. Записать честные ограничения, включая состояние интеграции корзины. |

У каждого из трёх участников должен быть собственный работающий вклад в официальном репозитории: backend/catalog/cart, frontend/chat/cart, AI/orchestration/evaluation. Файлы и контракт распределить до одновременного редактирования. Делать небольшие осмысленные коммиты.

## Приёмка перед сдачей

1. Существующий артикул даёт проверенные характеристики, наличие и ссылку на сертификат, если сертификат реально найден.
2. Позиция с нулевым остатком даёт хотя бы один релевантный доступный аналог и объяснение различий.
3. Вопрос об оплате, доставке и минимальной партии получает содержательный ответ с источником и честным указанием неизвестного/противоречивого.
4. Просьба «добавь» до явного подтверждения не меняет корзину; подтверждение учитывает количество, остаток, повторный запрос и смену остатков.
5. Ссылка после добавления открывает именно обновлённую корзину. Для утверждения «корзина ekt.kz» нужна отдельная проверка на сайте партнёра.
6. Всё воспроизводится по README из чистого клона. Нет секретов в Git, frontend, логах и примерах запросов.

Данные API ekt.kz, страницы сайта, OpenAI-модель и библиотеки — внешние материалы; перечислить их в README. Синтетическую выборку при использовании маркировать как синтетическую.

## Решения, которые нужны от партнёра

В первую очередь: поддерживаемый способ записи в тестовую корзину ekt.kz и связь с сессией сайта; пример товара с сертификатом; правило минимальной партии и актуальный порог бесплатной доставки. Если write-интеграции нет, прямо согласовать, принимает ли жюри отдельную корзину прототипа как демонстрацию механики. Без такого согласования пятый пункт нельзя считать полностью выполненным.
