# RedRed — проверенный курс для кейса ekt.kz

Дата ревизии: 2026-09-23. Общий контракт v3 — [BACKEND_SPEC.md](BACKEND_SPEC.md): WebSocket-чат, типизированные события и ограниченный путь обработки. Основное хранилище — PostgreSQL. AI подключён через `backend/assistant/service.py`: реальный HTTP-прогон проверил условия, товар, подтверждение и аналоги. После проверки инструментов текст передаётся частями из потокового ответа OpenAI; пользовательский интерфейс ещё не завершён. Реализованное состояние и запуск описаны в README. Ниже также сохранены цели следующих этапов, которые не следует считать уже реализованными.

## Решение по гипотезе

Направление верное: ассистент понимает свободный запрос, а факты о товарах получает из каталога; подтверждение и изменение корзины контролируются сервером. Прежний план пытался реализовать полный обход каталога, vector RAG, все форматы вложений и обширный eval-набор одновременно с обязательным сценарием. Сейчас backend/AI-путь проверен через HTTP; следующий приоритет — рабочий frontend и браузерная приёмка. Nginx, расширение retrieval и дополнительные форматы не должны задерживать основной сценарий.

Два ограничения фиксируем явно; разработка не блокируется ожиданием ответа партнёра:

1. Предоставлены только `GET /api/products` и `GET /api/products/detail?id=...`. Они не дают права или способа изменить корзину ekt.kz. Адрес существующей корзины сайта — `https://ekt.kz/personal/cart/`, но простая ссылка на него не перенесёт товары из корзины нашего прототипа. Нужны согласованный write API/SDK, тестовая среда или разрешённый способ интеграции с сессией сайта. До этого локальная корзина может демонстрировать логику подтверждения, но не закрывает интеграцию с реальной корзиной ekt.kz и переход к оформлению на сайте.
2. Условия покупки опубликованы на `https://ekt.kz/checkout-delivery/`, однако другие блоки сайта содержат иные пороги бесплатной доставки по Алматы. Для ответа можно использовать бесспорные способы оплаты и общие условия доставки со ссылкой на официальный раздел. Основной текст указывает 30 000 ₸, повторяющийся блок — 15 000 ₸. Пока конфликт не разрешён, не обещать бесплатную доставку без оговорки. Общего правила минимальной партии пока нет; для отдельных товаров на сайте встречается поле «Кратность (мин)». Нельзя объявлять его общим правилом магазина.

## Что действительно известно о данных

- Партнёр предоставил Basic Auth и три read endpoint: `GET https://ekt.kz/api/products`, страницы списка `?page=N` и `GET https://ekt.kz/api/products/detail?id=...`. Логин и пароль не записывать в Git, frontend, документацию или логи. Хранить только в переменных окружения backend; `.env.example` должен содержать пустые `EKT_API_USERNAME` и `EKT_API_PASSWORD`.
- Проверка API 2026-09-23: список содержит ID, артикулы, названия и URL; детали — цену, `quantity`, `stores`, `properties`. Выгрузка дала **15 035 уникальных ID**: при `per_page=100` страница 151 вернула 35 позиций. Проверены **11 258 подробных карточек**, после чего обход остановлен владельцем. Дальние страницы могут повторять первую: непустая страница 1600 не доказывает наличие 32 000 товаров. Импорт останавливается на пустой/неполной странице, повторе страницы или отсутствии новых ID. Это размер конкретной выгрузки, не постоянная величина; повторный полный обход не нужен.
- Отдельный ограниченный AI-probe сначала получил 3 страницы и 10 из 12 карточек: средняя задержка detail составила около 6,25 с, две карточки завершились таймаутом. Следующий короткий прогон не получил даже список после двух попыток; сохранённый отчёт этого прогона имеет статус `partial`. Поиск работает по локальному индексу, а live-проверка остатка имеет timeout и обязательна повторно перед подтверждением корзины. При недоступности API подтверждение блокируется.
- В карточке `id=515291` ранее отмечен конфликт: название/описание указывали 160 А, поле `properties.NOMINALNYY_TOK` — 250 А. При таком конфликте показать оба значения и не использовать спорный параметр для доказательства совместимости.
- Документы найдены у товара **21449**, артикул `010500006_`: `properties.FILES_CERTIFICATES` содержит ID 192137–192140, также есть паспорта и схемы. На [странице товара](https://ekt.kz/catalog/nizkovoltnaya_apparatura/modulnye_avtomaticheskie_vyklyuchateli/va_47_29_3_63_a_iek/va47_29_1f_16a_iek_12_144_/) найдены ссылки на [сертификат 004 MVA20-1-016-C](https://ekt.kz/upload/iblock/d73/cg4iz2mfi5d8v86yygje3moxllyoq0w2/Sertifikat-004-MVA20_1_016_C.pdf), декларацию, отказные письма и инструкции. ID файла не является URL. `url` — страница товара, `url_api_detail` — JSON. Содержание и срок действия документов не проверялись, единой схемы для всего каталога нет. Сохраняем найденные ссылки с типом и источником; отказное письмо не выдаём за сертификат, адрес по ID не придумываем.
- Репрезентативная выборка допустима по условиям кейса. Начальный локальный индекс строить из ограниченного числа страниц и заранее проверенных артикулов для демонстрации. Для товара вне индекса отвечать, что он не найден в проверенной выборке, а не что его нет во всём магазине. Полный обход каталога требует согласования лимитов API и времени.

## Минимальная архитектура

```text
Целевая схема (Nginx и frontend-интеграция ещё не реализованы):
Nginx: единая точка входа и проксирование /api
  -> React: чат и карточки товаров, подтверждение, просмотр корзины
  -> FastAPI: сессия, поиск, проверка фактов, AI-оркестрация, cart guard
       -> ekt.kz read API: живые детали, цена и остаток
       -> локальный индекс выборки: ID, артикул, название, несколько параметров
       -> официальный документ условий покупки
       -> OpenAI Responses API: понимание запроса и формулировка ответа
       -> PostgreSQL: каталог, история, сессии, предложения и корзина прототипа
```

Используются FastAPI и PostgreSQL; React/Vite-проект есть, но пользовательский интерфейс ещё не собран. `compose.yaml` запускает только БД; Nginx и контейнеризация всего приложения пока не реализованы. Redis/Redis Stack, embeddings и vector search не нужны для первой версии. PostgreSQL выбран для конкурентных транзакций и поиска, а не как гарантия ускорения внешних API. Retrieval начинается с точного артикула и поиска по ограниченной выборке с живой detail-проверкой. Если партнёр предоставит интеграцию реальной корзины, заменить только адаптер корзины, сохранив серверную проверку подтверждения.

### Граница ответственности ИИ

- Модель извлекает намерение, артикул/описание, количество, задаёт уточнение и формулирует ответ на языке пользователя.
- Поиск точного артикула, сравнение технических параметров, источник фактов, арифметика остатков, подтверждение и запись корзины выполняются кодом backend.
- Стык модуля — `async reply(context, tools, emit) -> AssistantResult`. Callback emit передаёт `text.delta`/`status`, результат возвращает language/text/product_ids/proposed_items/warnings. Read-инструменты: `search_catalog(query, article, limit)`, `get_product(product_id)`, `find_analogs(product_id, required_quantity)`, `get_purchase_terms()`, `get_cart()`. Backend валидирует результат и создаёт pending-предложение. Инструмента записи в корзину у модели нет. Полный контракт и владельцы файлов — разделы 2 и 8 BACKEND_SPEC.
- Вызовы модели и её структурированный вывод валидируются. Текст карточек и вложений считается данными, а не инструкциями. При сбое модели точный поиск по артикулу и сведения из карточки продолжают работать без выдуманного AI-ответа.
- Основная модель прототипа — `gpt-6-sol`: официальная OpenAI Docs подтверждает текст, изображения, function calling и structured outputs в Responses API (`https://developers.openai.com/api/docs/models/gpt-6-sol`). Доступ на ключе команды проверен 2026-09-23: базовый набор прошёл 9/9, диалоговый mock tool loop с текущей схемой `proposed_items` — 5/5. Модель остаётся конфигурируемой через `OPENAI_MODEL`.
- Отдельный streaming probe Responses API показал первое SSE-событие за 1,098 с, первый текстовый delta за 2,170 с и завершение за 2,402 с в одном пробном запросе. Это ориентир, не SLA; на демо измеряем серию прогонов и отдельно учитываем медленные tools.

### Сессия, история, языки и вложения

- PostgreSQL хранит Session, Message, ProductSnapshot, Cart/CartItem, CartProposal и Attachment. Предложение живёт 10 минут; сессия, история и корзина — 24 часа. Вложения находятся на диске, в БД — метаданные/extraction; удаление файлов через 1 час. Цена, остаток и подтверждение не восстанавливаются из LLM-summary.
- На запрос модели передаются инструкции, язык, текущее сообщение, ограниченная история диалога и состояние корзины/предложения; отдельный summary старой части сейчас не реализован. История управляется backend; вызов Responses API использует `store=false`.
- Ассистент отвечает на русском, казахском или английском. Явный выбор языка сохраняется в сессии; иначе используется язык текущего сообщения. Артикулы, бренды, числа и единицы не переводятся. Одинаковые контрольные сценарии прогоняются на всех трёх языках.
- DOCX/XLSX разбираются локально с ограничением объёма; JPEG и PDF передаются модели. Локальный разбор PDF и OCR сканов не реализованы, а полный AI-сценарий по этим форматам не проверен. Содержимое файлов считается недоверенными данными, не попадает в общий индекс и удаляется по TTL.

### Данные продукта

Backend возвращает карточку из раздела 4 BACKEND_SPEC: `id`, `article`, `supplier_article`, `name`, `category`, `product_url`, `image_url`, `price`, `currency`, `available_quantity`, `stock_scope`, `unit`, `quantity_step`, `stores`, `description`, `characteristics`, `documents`, `checked_at`, `data_warnings`. Деньги и количества — десятичные строки; расчёты — Decimal. Сырой `quantity` партнёра нормализуется в `available_quantity`. Цена и наличие при ответе и перед подтверждением перечитываются из детального API. Остаток по складам и город пользователя не смешивать: если доступен только общий остаток, не обещать наличие в конкретном городе.

Аналог предлагать из той же товарной категории с проверенными ключевыми параметрами и положительным актуальным остатком. Ответ должен назвать совпадения и существенные отличия. Если строгая совместимость не доказана, писать «похожий товар, проверьте совместимость», а не «полный аналог». Для теста заранее найти одну реальную отсутствующую позицию и один реальный доступный кандидат в выборке.

### Корзина

1. Backend создаёт предложение с товарами, количеством, проверенными ценами, случайным `proposal.id`, базовой revision корзины, сроком и привязкой к сессии. UI показывает состав и кнопку «Да, добавить». Действующее предложение одно, новое заменяет старое.
2. Модель и неявные фразы корзину не меняют. `POST /api/cart/proposals/{id}/confirm` принимает `{"confirmed":true}`, проверяет владельца, CSRF, срок, revision и статус. Текст «да, добавь» проверяется сервером до модели по правилам раздела 7 BACKEND_SPEC.
3. Backend получает свежие цену и остаток до транзакции. Проверяет положительное количество, шаг и итог с учётом уже добавленного. Нехватка остатка, нулевая/неизвестная цена или сбой ekt.kz блокируют операцию. Изменённая цена требует нового предложения и согласия; количество молча не уменьшается.
4. PostgreSQL-транзакция блокирует корзину/предложение в едином порядке и повторно проверяет revision. Добавляются все строки либо ни одна. `proposal.id` — ключ идемпотентности: повтор возвращает сохранённый результат, не добавляет второй раз. Статусы: pending, confirmed, cancelled, expired, replaced.
5. Ссылка ведёт на `/cart` прототипа. `https://ekt.kz/personal/cart/` нельзя выдавать как результат без проверенной интеграции. Локальная корзина не резервирует склад и не оформляет заказ на ekt.kz.

Случайный токен сессии — в HttpOnly/SameSite-cookie, Secure при HTTPS. Мутации защищаются CSRF и проверкой Origin. Цены клиента не являются источником истины; платёжные данные не запрашиваются.

## Быстрый сценарий

Локальный поиск → до трёх свежих карточек → проверенный ответ. Реализованный AI-сервис выполняет не более двух вызовов модели; текст отправляется одной дельтой после валидации, а не потоком токенов. При нехватке данных нужно задать уточнение. Подтверждение действующего предложения обрабатывает backend без модели.

Повторные инструменты используют данные текущего запроса; при новом подтверждении остаток и цена проверяются заново. Условия, ссылки на документы и индекс готовятся заранее. Не обходить сайт, не строить индекс и не генерировать summary на пути каждого сообщения. Короткий ответ — до 120 слов и трёх карточек. Метаданные для предложения берутся из проверенного намерения/инструментов, отдельный LLM-вызов для упаковки JSON не нужен.

Один процесс FastAPI, асинхронные клиенты с переиспользованием соединений, SQLAlchemy AsyncEngine/asyncpg. Разбор файлов — ограниченный executor. Без Redis, дополнительного микросервиса или очереди задач. Начальные пределы: три диалога и шесть запросов каталога одновременно; детали — раздел 8 BACKEND_SPEC.

Цели обычного текста: первый полезный результат ≤2 сек., полный p95 ≤5 сек.; общий deadline 8 сек. Таймаут не считается успешным ответом. Статус «печатает» не считается полезным результатом. Вложения проверяются отдельно на небольших файлах; предел 20 сек. не означает выполнения требования кейса. После реализации достаточно 10 последовательных запросов и трёх параллельных с замером этапов. Эти показатели пока не измерены.

## Общий контракт v3

Схемы карточки, ошибок, сессии и корзины — в разделе 6 [BACKEND_SPEC.md](BACKEND_SPEC.md). Это маршруты прототипа, не API ekt.kz.

```text
POST /api/session
GET  /api/products
GET  /api/products/{id}
GET  /api/products/{id}/analogs
GET  /api/purchase-conditions
POST /api/attachments
GET  /api/attachments/{attachment_id}
GET  /api/chat/messages
POST /api/chat/messages
WS   /api/chat/ws
GET  /api/cart
POST /api/cart/proposals
POST /api/cart/proposals/{id}/confirm
POST /api/cart/proposals/{id}/cancel
GET  /health/
GET  /ready
```

`GET /cart` — страница фронтенда. Прямого DELETE позиции нет: изменение состава тоже требует подтверждения.
Основной чат — WS /api/chat/ws. Клиент отправляет message.send с `{request_id, text, attachment_ids: [], language: null}`; язык — ru/kk/en/null. HTTP POST /api/chat/messages — резервный транспорт того же обработчика, не второй способ повторно выполнить запрос.
События `{type, request_id, seq, data}`: message.accepted, processing.status, products.ready, assistant.delta, assistant.completed, error. Дельты передаются сразу, а итоговые карточки/корзина/предложение проверяются сервером. Cookie и Origin проверяются при handshake. Файлы и кнопка подтверждения остаются HTTP. Nginx/Vite пропускают WebSocket Upgrade.
Один активный запрос на сессию, одинаковый request_id в HTTP/WS защищает от повторного запуска. После разрыва — переподключение и чтение истории; завершённый результат сохраняется до отправки completed. Детали ошибок, повторов и восстановления — раздел 6 BACKEND_SPEC.
Ответ: `message_id`, `language`, `text`, `products[]`, `warnings[]`, `proposal`, `cart`, `cart_url`.
Подготовка принимает `{items: [{product_id, quantity: "2"}]}`; confirm — `{confirmed: true}`; cancel — `{}`.
Общее имя — `proposal.id`, не `action_id`; поле — `proposal`, не `pending_action`.
UI использует серверные карточки, не извлекает цену/остаток/URL из текста модели.
Файл по `GET /api/attachments/{attachment_id}` доступен только владельцу сессии.
`/ready` проверяет PostgreSQL, не вызывает ekt.kz/LLM.

Реальные имена WebSocket-событий перечислены выше (`processing.status`, `assistant.delta`, `assistant.completed` и др.). Для запросов с инструментами backend может сразу отправить безопасный статус «Проверяю каталог», но не выдаёт цену, наличие, характеристики или обещание добавления до успешного tool call и серверной проверки. Сейчас сервис отправляет одну дельту с целиком проверенным текстом, не token streaming. Основная пользовательская метрика — время до первого полезного результата; отдельно нужны время tools, модели и полное время ответа, иначе быстрый статус скроет медленный каталог.

Логи пишутся структурированным JSON: `request_id`, хеш сессии, событие, tool/model, статус, `ttft_ms`, `tool_duration_ms`, `completion_ms` и `duration_ms`. Не логировать Basic Auth, API-токены, cookie, полные пользовательские документы и платёжные данные.

## Исходный план на 5 часов (не отчёт о выполнении)

| Время | Разработка и проверяемый результат |
| --- | --- |
| 00:00–00:30 | Команда использует проверенную схему API и найденные документы/условия, фиксирует ограничение локальной корзины, единый контракт, PostgreSQL, тестовые товары и границы выборки. Разработку не блокирует отсутствие ответа партнёра. |

Разработчик AI делает один рабочий Responses-вызов со структурированным намерением и fallback для точного артикула. Проверка: реальный артикул → верные факты и источник. |

## Приёмка перед сдачей

1. Существующий артикул даёт проверенные характеристики, наличие и ссылку на сертификат, если сертификат реально найден.
2. Позиция с нулевым остатком даёт хотя бы один релевантный доступный аналог и объяснение различий.
3. Вопрос об оплате, доставке и минимальной партии получает содержательный ответ с источником и честным указанием неизвестного/противоречивого.
4. Просьба «добавь» до явного подтверждения не меняет корзину; подтверждение учитывает количество, остаток, повторный запрос и смену остатков.
5. Ссылка после добавления открывает именно обновлённую корзину. Для утверждения «корзина ekt.kz» нужна отдельная проверка на сайте партнёра.
6. Всё воспроизводится по README из чистого клона. Нет секретов в Git, frontend, логах и примерах запросов.
7. WebSocket показывает первое полезное событие за единицы секунд, поток завершается итоговым структурированным `result`; факты о товаре появляются только после успешной проверки каталога. TTFT и полная задержка измеряются отдельно.

Данные API ekt.kz, страницы сайта, OpenAI-модель и библиотеки — внешние материалы; перечислить их в README. Синтетическую выборку при использовании маркировать как синтетическую.
